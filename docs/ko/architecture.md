# 아키텍처

## 시스템 개요

Bias Song Finder는 백엔드와 프론트엔드가 각각 독립 배포되는 풀스택 웹 애플리케이션입니다.

```
사용자 브라우저
    │
    ▼
Cloudflare Workers (Next.js)
    │  API 프록시
    ▼
fly.io (Spring Boot)
    ├── PostgreSQL (schema-per-tenant)
    └── Redis (세션 + rate limiting)
```

---

## 백엔드: Gradle 멀티모듈

백엔드는 각각 고유한 역할을 가진 세 개의 Gradle 모듈로 분리되어 있습니다.

| 모듈 | 역할 |
|--------|------|
| `:core` | 공유 도메인 로직, 엔티티, 서비스, 스키마 마이그레이션, 멀티테넌시 인프라 |
| `:api` | REST API 서버 (배포 대상) — 인증, rate limiting, API 문서화 |
| `:admin` | 어드민 UI 서버 (로컬 전용) — 데이터 관리 인터페이스 |

`:api`와 `:admin` 모두 `:core`에 의존합니다.

---

## 애플리케이션 경계

HTTP 어댑터는 도메인 서비스에 위임하고, 공유 영속성과 인프라는 `:core`에서 관리합니다. 퀴즈 엔진 내부에서는 질문 선택 정책, 선택지 생성, 답변 처리, 상태 전이, 결과 조립의 책임을 분리합니다. 전체 흐름을 하나의 서비스에 집중시키지 않아 개별 규칙을 테스트하기 쉽습니다.

---

## 멀티테넌시: Schema-per-Tenant

각 아티스트 그룹(예: SHINee, f(x))은 모든 도메인 테이블을 포함하는 독립된 PostgreSQL 스키마를 가지며, 공유 메타데이터는 공통 스키마에 위치합니다.

주요 특징:
- **다중 레이어 테넌트 해석** — 활성 세션과 세션 만료 후 영속 공유 링크의 테넌트 컨텍스트를 단계적으로 해석
- **검증된 스키마 라우팅** — SQL 구성 전에 테넌트 식별자를 검증하며, 테넌트 커넥션에서 공유 도메인 테이블로의 fallback을 허용하지 않음
- **커넥션 정리** — 커넥션 재사용 전에 스키마를 초기화하며, 설정 또는 정리에 실패한 커넥션은 폐기

## 세션 기반 게임 흐름

사용자 로그인이 필요하지 않습니다. 세션 키가 사용자 식별자 역할을 합니다.

플로우는 단순한 사이클을 따릅니다:
1. **세션 생성** — 해당 테넌트의 곡 카탈로그에서 후보곡 풀 초기화
2. **질문 루프** — 백엔드가 다음 질문을 선택하고, 사용자가 답변하면 후보곡이 필터링됨
3. **결과** — 후보곡이 한 곡으로 좁혀지면 퀴즈 종료

모든 세션 상태는 외부 저장소에 보관되어(인메모리 아님) 백엔드의 수평 확장이 가능합니다.

### Graceful Fallback

답변 제출은 매칭 성공, 매칭 실패, 질문 소진을 명시적인 상태로 반환하고 해당하는 경우 유사 곡을 함께 제공합니다. 질문이 소진되면 마지막 질문을 다시 열거나 매칭 실패 결과로 진행할 수 있습니다. 다음 질문 조회는 후보가 없거나 질문이 소진된 경우 기존의 에러 응답을 유지합니다.

### 상태 일관성

Redis 갱신은 세션의 예상 버전을 원자적으로 비교하고 남은 TTL을 보존합니다. 오래된 상태의 갱신과 중복 답변은 최신 진행 상태를 덮어쓰지 않고 충돌로 반환합니다. 결과 생성은 데이터베이스 트랜잭션 잠금과 고유 제약을 사용하여 동시·반복 요청에도 세션당 활성 결과 하나를 유지합니다.

문제와 선택의 배경은 [기술적 의사결정](engineering-decisions.md)에 정리했습니다.

### 관측성 (로컬)
- **Loki + Promtail + Grafana** — 구조화된 세션 로그 수집 및 대시보드
- **Prometheus + Spring Boot Actuator** — 애플리케이션 메트릭을 수집해 Grafana로 노출
- Grafana 대시보드로 세션 퍼널, 답변 분포, 결과 만족도, 세션별 여정 추적
